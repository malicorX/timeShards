## Executive Summary

AI TimeShards is no longer just a prototype. It has a working Rust/Axum API, SQLite persistence, two Tauri/Svelte desktop apps, demo data, Germany-first time workflows, access-control concepts, smoke tests, CI, and useful docs. The strongest part of the project is that it already proves the product shape: time tracking, absences, timesheets, shifts, badges, zones, access rules, anti-passback, occupancy, audit, and a simulated/external hardware bridge all run through one local desktop/server model.

The weakest part is that the implementation has grown as a vertical slice rather than as a durable product architecture. Backend route modules and frontend app files are now very large, domain rules are often embedded directly in handlers, test coverage is mostly smoke-level, and several production-critical concerns are not yet hardened: API exposure, CORS, CSP, local token storage, SQLite foreign-key enforcement, transactional consistency, export escaping, hardware authentication, backups, installer/release defaults, and first-run onboarding.

The long-term roadmaps are split. `ROADMAP.md` describes a micro-kernel/shard platform, but the actual project is a pragmatic monolithic API plus two apps. `ROADMAP_DETAILS.md` describes a Primion-inspired Germany-first desktop product, and that is the roadmap the code actually follows. The right next move is not to chase both equally. The project should either commit to the pragmatic product path for the next 2-3 milestones, or pause feature work and intentionally refactor toward the kernel vision. My recommendation is: keep the pragmatic product path, harden it for a staged pilot, and downgrade the micro-kernel roadmap to a later architectural option.

Overall rating: 6.5 / 10 for MVP/product discovery, 4.5 / 10 for production readiness.

## Major Findings

Severity scale:

- P0: critical, must fix immediately.
- P1: high priority before production or customer pilot.
- P2: important engineering/product improvement.
- P3: cleanup or later enhancement.

### P1 - API exposure is too permissive for production

Evidence:

- `crates/timeshards-api/src/server.rs` defaults `TIMESHARDS_API_HOST` to `0.0.0.0`.
- The same file uses `CorsLayer::new().allow_origin(Any).allow_methods(Any).allow_headers(Any)`.
- `apps/server/src-tauri/tauri.conf.json` and `apps/client/src-tauri/tauri.conf.json` set `"csp": null`.
- `apps/server/src/lib/api.ts` and `apps/client/src/lib/api.ts` store bearer tokens in `localStorage`.
- `README.md` and `docs/GETTING_STARTED.md` encourage LAN access.

Why it matters:

This is fine for a LAN demo but not for production. A LAN-exposed API with permissive CORS and bearer tokens in localStorage needs a clear threat model. The product handles employee time, access logs, badges, and audit data. That is sensitive HR/security data.

Recommended fix:

- Default production bind should be explicit and conservative.
- Make `TIMESHARDS_API_HOST=127.0.0.1` the default unless LAN mode is explicitly enabled.
- Replace `CorsLayer::Any` with an allowlist derived from config.
- Add a production health warning when host is non-loopback and demo/default-password settings are unsafe.
- Add a real Tauri CSP.
- Move tokens out of unbounded localStorage if possible, or reduce token lifetime and add refresh/re-login UX.
- Document a production network model: local-only, LAN trusted subnet, or reverse proxy/TLS.

### P1 - SQLite foreign keys are declared but not explicitly enforced

Evidence:

- Migrations define many `REFERENCES` clauses in `crates/timeshards-db/migrations/001_initial.sql`.
- `crates/timeshards-db/src/pool.rs` creates `SqliteConnectOptions` but does not enable `PRAGMA foreign_keys = ON` or use a connect option for foreign keys.

Why it matters:

SQLite does not enforce foreign keys unless enabled per connection. Without that, invalid employee IDs, orphan badges, dangling rules, and inconsistent timesheet/access data can enter the DB. This is especially risky because many handlers trust IDs from request bodies.

Recommended fix:

- Enable SQLite foreign keys on every connection.
- Add a migration or startup check that validates existing orphaned data.
- Add tests proving invalid FK inserts fail.
- Consider adding CHECK constraints for status/kind fields.

### P1 - Multi-step writes are not transactional

Evidence examples:

- `crates/timeshards-api/src/routes/admin.rs` creates a user, role link, employee, default access rule, and audit row in separate statements.
- `create_employee` creates employee, optional badge, optional access rule, and audit separately.
- `process_credential` inserts an access event and a domain event separately.
- Timesheet bulk operations loop over updates and often count partial success.

Why it matters:

If a later insert fails, the system can leave partially-created users, employees without role links, badges without expected rules, access events without matching domain events, or audits that do not match actual state.

Recommended fix:

- Introduce transaction boundaries for business operations.
- Add repository/service functions for multi-write operations.
- Return explicit partial-success results only where partial success is intentionally allowed.

### P1 - HTML and CSV exports are injection-prone

Evidence:

- `crates/timeshards-api/src/routes/reports.rs` writes employee names, zones, doors, status, and raw-derived fields directly into CSV and HTML using `format!`.
- `apps/server/src/lib/api.ts` opens HTML export content with `window.open` and `document.write`.

Why it matters:

Employee names, zone names, door names, or reason text can contain HTML or spreadsheet formulas. Current exports can produce stored XSS in HTML reports and CSV formula injection in Excel/LibreOffice workflows. This is especially relevant for HR/admin exports.

Recommended fix:

- HTML-escape every exported field.
- CSV-quote according to RFC 4180 or a deliberate semicolon CSV dialect.
- Prefix dangerous spreadsheet-leading characters (`=`, `+`, `-`, `@`, tab, CR) when exporting to CSV.
- Add regression tests for malicious names.

### P1 - Date/time validation compares strings instead of parsing timestamps

Evidence:

- `crates/timeshards-api/src/validation.rs` implements `validate_interval` as `if ends_at <= starts_at`.
- Many endpoints pass RFC3339 strings through and rely on lexical ordering.

Why it matters:

RFC3339 strings with offsets can be chronologically valid but lexically misleading. Invalid dates can also leak deeper into the system until SQLite or later parsing fails. Time tracking and absences are the core product; interval validation must be exact.

Recommended fix:

- Parse `starts_at` and `ends_at` as `DateTime<Utc>` once at the API boundary.
- Store canonical UTC RFC3339 strings.
- Return structured validation errors.
- Add tests for timezone offsets, invalid timestamps, DST boundaries, and end-before-start.

### P1 - Automated tests are too thin for the amount of domain logic

Evidence:

- `cargo test --workspace` passes, but only `timeshards-hardware` has 5 unit tests.
- API, DB, access evaluation, time transitions, timesheet rebuild, RBAC scoping, reports, and UI flows have no focused unit/integration tests.
- CI relies heavily on smoke scripts.

Why it matters:

Smoke tests are valuable but broad. They do not catch edge cases like malformed punch sequences, cross-employee data leaks, weird RFC3339 offsets, FK enforcement, export injection, or transactional rollback.

Recommended fix:

- Add Rust integration tests around API routes with fresh SQLite DBs.
- Add focused tests for:
  - time transition state machine
  - timesheet rebuild
  - ArbZG warnings
  - access decisions
  - anti-passback
  - RBAC scoping
  - reports escaping
  - production login policy
- Add at least a small frontend unit/component test layer or Playwright smoke for critical UI flows.

### P1 - Hardware ingress is unauthenticated and unaudited as a trusted source

Evidence:

- `crates/timeshards-hardware/src/tcp_ingest.rs` accepts newline-delimited TCP lines and pushes them to the hardware channel.
- There is no authentication, signing, replay protection, source allowlist, sequence ID, deduplication, or TLS.
- `docs/HARDWARE.md` correctly says this is a bridge/test path, not a full OEM protocol.

Why it matters:

If TCP ingest is ever bound beyond loopback, anyone on that network path can create access decisions or door alarms. Even on loopback, a local process can inject badge events.

Recommended fix:

- Keep TCP ingest loopback-only by default.
- Add an HMAC/API-key header or signed JSON envelope for external forwarders.
- Add replay/deduplication via event IDs and timestamps.
- Include hardware source identity in audit/domain events.
- Treat `external` mode as not production-ready until these are done.

### P1 - Access evaluation has demo-friendly fail-open paths

Evidence:

- `crates/timeshards-api/src/access_eval.rs` grants access when a door has no zone.
- The same evaluator grants access when a zone has zero access rules.
- `crates/timeshards-api/src/schedule.rs` treats invalid or unparseable schedules as allowed.
- Scan-time evaluation relies on badge revocation for deactivated employees rather than checking `employees.active_to` directly.

Why it matters:

These defaults are convenient for demos, but production access control should generally fail closed. In a Primion-like system, an admin who creates a zone with no rules is more likely to expect "nobody is allowed yet" than "every active badge is allowed." Invalid schedules should not silently open access windows.

Recommended fix:

- Switch production access evaluation to deny-by-default for zoned doors.
- Treat malformed schedules as `deny` with a specific `schedule_invalid` reason.
- Add an explicit "open zone" mode if demo/open-access behavior is desired.
- Check employee active status during credential evaluation.
- Add tests for no-zone, no-rules, malformed schedule, deactivated employee, and explicit allow cases.

### P2 - Route modules are too large and mix HTTP, SQL, authorization, and domain logic

Evidence:

- `crates/timeshards-api/src/routes/time.rs`: about 1427 lines.
- `crates/timeshards-api/src/routes/admin.rs`: about 1391 lines.
- `crates/timeshards-api/src/routes/access.rs`: about 1387 lines.

Why it matters:

The product is entering the phase where every new feature will touch the same giant files. That increases merge conflicts, makes review harder, and hides domain invariants inside handlers.

Recommended fix:

- Keep route files thin.
- Extract services:
  - `time_service`
  - `timesheet_service`
  - `absence_service`
  - `access_service`
  - `employee_service`
  - `report_service`
- Extract query/repository helpers where transaction boundaries matter.
- Move DTOs near route modules but domain decisions into service modules.

### P2 - Frontend architecture is already at the limit

Evidence:

- `apps/server/src/App.svelte`: about 2880 lines.
- `apps/client/src/App.svelte`: about 1198 lines.
- Most state, API orchestration, rendering, and inline styles live in these files.
- `svelte-check` reports 10 accessibility warnings in server forms.

Why it matters:

The UI proves the workflows, but future work will be slow and risky. It is hard to test, hard to scan, and hard to assign ownership. The server app in particular is becoming an all-in-one admin console file.

Recommended fix:

- Split by feature:
  - `Overview.svelte`
  - `Personnel.svelte`
  - `TimeAdmin.svelte`
  - `AbsenceAdmin.svelte`
  - `AccessAdmin.svelte`
  - `SystemSettings.svelte`
  - client equivalents
- Extract API stores/services:
  - `authStore`
  - `timeApi`
  - `accessApi`
  - `adminApi`
- Replace most inline styles with component classes.
- Fix label/control associations.
- Add a small UI regression harness for login, clock-in, timesheet, access scan, and manager approval.

### P2 - Production UI still exposes demo affordances in the server app

Evidence:

- `apps/client/src/App.svelte` hides demo login shortcuts when default passwords are blocked.
- `apps/server/src/App.svelte` still shows quick-fill buttons for `admin` / `demo` / `manager` in the login area.
- The server System tab documents demo credentials even when production/default-password-blocking flags are active.

Why it matters:

The API may reject default passwords, but the admin UI still visually teaches operators to use them. That is confusing during staging/production cutover and weakens the otherwise good production-mode story.

Recommended fix:

- Gate server demo quick-fill buttons on the same health flags the client uses.
- Hide or relabel demo credential docs when `demo_seeding_enabled=false` or `default_password_login_blocked=true`.
- Add a UI smoke/assertion for production login mode.

### P2 - Audit hash chain is weaker than it looks

Evidence:

- `crates/timeshards-db/src/audit.rs` hashes only `id`, `action`, `object_type`, `object_id`, and `occurred_at`, plus prior hash.
- It does not include `actor_type`, `actor_id`, `reason`, `before_json`, or `after_json`.

Why it matters:

The UI and roadmap imply audit/compliance value. A hash chain that omits important fields does not protect the actual contents users care about. It may create a false sense of immutability.

Recommended fix:

- Include all audit row fields in a canonical JSON hash payload.
- Add a verification function for the chain.
- Add smoke/test coverage that detects tampering.
- Consider append-only constraints or at least admin UI warnings that this is tamper-evident, not tamper-proof.

### P2 - OpenAPI and API docs drift

Evidence:

- `docs/API.md` lists about 66 API rows.
- `docs/openapi.json` contains about 28 `/api/v1` path entries.
- README explicitly calls OpenAPI a subset.

Why it matters:

If this product expects hardware forwarders, integrations, or payroll connectors, API contracts need to become reliable. A partial OpenAPI file is okay for demos but not for integrators.

Recommended fix:

- Decide whether OpenAPI is authoritative.
- Generate it from route declarations or keep a disciplined update checklist.
- Cover all stable endpoints and response schemas used by apps/scripts.

### P2 - Roadmap mismatch is now a planning risk

Evidence:

- `ROADMAP.md` promises micro-kernel, shard modules, event bus, widget UI, and adapter layers.
- The code has a small `timeshards-kernel`, but business logic is mostly in monolithic API route modules.
- `ROADMAP_DETAILS.md` describes the Primion-like product direction, which the code actually follows.

Why it matters:

The team may make bad prioritization choices if it treats the micro-kernel roadmap as current truth. The project is succeeding as a pragmatic time/access product, not yet as a modular platform.

Recommended fix:

- Rewrite `ROADMAP.md` to separate "current product roadmap" from "future platform architecture."
- Add a decision record: pragmatic monolith now, kernel later only if module marketplace/third-party extensions become a business requirement.

### P2 - Time/compliance logic is useful but not legally deep enough

Evidence:

- `crates/timeshards-db/src/policy.rs` supports max daily, max weekly, regular minutes, and minimum break after threshold.
- Warnings are strings returned on rebuild.
- Policy JSON currently only deserializes max daily and max weekly from stored JSON.

Why it matters:

"Germany-first" is a strong positioning claim. Current rules are a good start, but not enough for real HR confidence.

Recommended fix:

- Model warning codes, not only strings.
- Store policy evaluation results per timesheet/day.
- Support configurable break thresholds (for example 6h/9h break rules).
- Add UI actions for warnings: acknowledge, correct, explain, export.
- Add tests for DE-specific edge cases.

### P2 - Time event state is too implicit

Evidence:

- Current clock state is derived from the last event kind.
- Corrections bypass transition validation.
- Timesheet computation tolerates malformed sequences by ignoring/closing intervals in simple ways.

Why it matters:

Manual corrections are essential, but they can create sequences that produce surprising timesheets. For a time-tracking product, sequence validity and correction auditability are core.

Recommended fix:

- Extract a time-event state machine and test it thoroughly.
- Add warnings for unmatched events, overlapping intervals, duplicate clock-ins, and open shifts.
- Rebuild affected timesheets after corrections or explicitly mark them stale.

### P2 - Report/export formats are demo-grade

Evidence:

- Timesheet export has CSV/HTML only.
- HTML tells users to print to PDF.
- No DATEV/payroll export contract.

Why it matters:

For German HR buyers, "how do I close the month and hand data to payroll?" is likely more important than additional dashboard widgets.

Recommended fix:

- Define one payroll-oriented export target.
- Add monthly closing workflow.
- Include approval/audit metadata in exports.
- Add a report preview that explains filters and scope.

## Security Review

Security strengths:

- Passwords are hashed with Argon2.
- Bearer tokens are stored hashed in DB.
- Sessions expire.
- Disabled users have sessions cleared.
- Password resets clear sessions.
- Production/staging default-password blocking exists and is smoke-tested.
- RBAC checks are widespread.

Security risks:

- API binds to all interfaces by default.
- CORS allows every origin.
- Tauri CSP is disabled.
- Tokens live in localStorage.
- TCP hardware ingress is unauthenticated.
- No rate limiting on login.
- No account lockout or brute-force defense.
- No TLS story for LAN.
- No CSRF/origin story beyond bearer auth.
- Export HTML is not escaped.
- Audit hash omits important fields.

Priority security plan:

1. Secure defaults: loopback bind by default, explicit LAN mode, restricted CORS.
2. Production guardrail: refuse startup or show red health when demo/default passwords and LAN exposure coexist.
3. Export escaping and CSV formula protection.
4. Hardware ingress authentication.
5. Login throttling/account lockout.
6. CSP and token-storage review.

## Data Integrity Review

Strengths:

- Schema is reasonably normalized for an MVP.
- Migrations are simple and readable.
- Domain objects use UUIDs.
- Audit and domain-event tables exist.
- Many status transitions are guarded in handlers.

Risks:

- SQLite foreign keys not explicitly enabled.
- Few CHECK constraints for status/kind/mode fields.
- Multi-step business writes are not transactional.
- Auto employee numbering from `COUNT(*)` can collide under concurrency or after deletion/manual numbers.
- Dynamic SQL is mostly safely bound, but duplicated and hard to reason about.
- Timesheet computation is tolerant rather than diagnostic for malformed event streams.

Priority data plan:

1. Enable and test foreign keys.
2. Add transactions around create/update workflows.
3. Add status/kind CHECK constraints in future migrations.
4. Add diagnostic warnings for malformed time event sequences.
5. Add an integrity check endpoint/script for pilot deployments.

## Backend Code Quality

Good:

- Straightforward Axum route structure.
- SQL parameters are bound, not interpolated, in most dynamic queries.
- Clear helper functions for auth, permissions, and access evaluation.
- Hardware boundary is clean enough for next adapters.
- Error messages are user-facing German in many paths.

Bad:

- Route modules are too long.
- Handler logic mixes auth, validation, SQL, domain decisions, persistence, events, and auditing.
- Validation is inconsistent across endpoints.
- There are limited typed request/response contracts.
- Domain events are persisted manually in several places rather than through one event store.
- Audit write failures sometimes fail operations, sometimes are ignored.
- Many operations use strings for statuses/kinds instead of enums.

Recommended backend refactor sequence:

1. Extract pure domain functions first, with tests.
2. Extract service modules around transaction boundaries.
3. Keep route handlers as auth + parse + call service + map response.
4. Introduce typed enums for statuses and event kinds.
5. Centralize domain-event and audit persistence.

## Roadmap Alignment

### `ROADMAP.md` - micro-kernel/shards

Status: mostly aspirational.

Implemented pieces:

- A small `timeshards-kernel` crate exists.
- There is an `EventBus`.
- Domain events are persisted.

Not implemented:

- Real module lifecycle used by time/access.
- Business logic as independently loaded shards.
- Widget registration.
- Slot UI.
- Storage adapters.
- Marketplace/gallery.
- Third-party shard contracts.

## Product Direction

The project has two possible identities:

1. Modular time-tracking platform with shards and marketplace.
2. Germany-first desktop time/access system inspired by Primion.

The code is already much closer to identity 2. That is the better near-term business path because it has visible customer value. The shard/platform idea may become valuable later, but it should not drive the next milestone unless the actual goal is developer ecosystem/marketplace.

Recommended strategic decision:

- For the next 3-6 months, call AI TimeShards a Germany-first desktop time and access-control product.
- Treat the kernel/shard architecture as a future refactor trigger, not the active roadmap.
- Update `ROADMAP.md` accordingly.
